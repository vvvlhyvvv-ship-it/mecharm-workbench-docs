## 一、需求与约束

### 1.1 招标条款要求

| 条款 | 要求 |
|---|---|
| 16（1） | HMI 及编程系统支持三维模型导入（设备本体 / 末端执行器 / 工件 / 产线场景），用于可视化编程、路径仿真、碰撞预检测 |
| 16（2） | 格式须包含但不限于 STEP(AP214/AP242)、IGES、STL、JT；导入后保留几何尺寸、装配关系与运动副定义 |
| 16（3） | 与各运动轴实时联动，刷新 ≥10Hz；拖拽选点生成路径并自动碰撞检测；碰撞高亮 + 报警，**碰撞路径禁止下发** |
| 16（4） | 提供三场景界面截图；支持格式清单及单模型最大面数 / 文件大小规格；≥3 分钟演示视频 |
| 其他 | 提供 STEP/JT/**轻量化三维模型**（含运动副定义）及 ≥200 点 OPC UA 接口（关键数据 ≥10Hz），配合数字孪生平台联调 |

### 1.2 实际使用约束（现场调研结论）

| 模型类别 | 体量 | 导入方式 | 控制方 |
|---|---|---|---|
| 压机、机械臂、加热炉、液压站、产线工装 | 大 | 交付前预处理后导入 | **我方可控** |
| **模具、锻件、客户工件** | **单件 ≥200 MB** | **客户现场直接导入，无预处理环节** | **客户直接控制** |

### 1.3 由约束推导出的三条技术要求

1. **运行时必须吃得下 200 MB 级单文件。** 客户不会为我们的软件做格式转换或简化。
2. **解析环节必须脱离浏览器地址空间限制。** 浏览器 WASM 的 32 位地址空间无法承载 200 MB 级 STEP 的中间数据。
3. **固定设备与客户模型必须走两条不同的处理路径。** 前者可离线做重压缩，后者必须在线实时完成。

## 二、核心技术矛盾分析

### 2.1 两条候选路线

| 项 | 路线 A（现状） | 路线 B（规程） |
|---|---|---|
| 几何内核 | occt-import-js（WASM 裁剪版，仅导入） | OCCT 原生 C++（B-Rep 全功能） |
| 三维渲染 | three.js + WebGL2 | OCCT AIS / VTK |
| 上层语言 | JavaScript / Node | Python（PySide6 / pythonocc-core） |
| 交付形态 | Web / Tauri 单 EXE | 桌面应用 |

### 2.2 量级测算

按实测基线（2.13 MB STEP → 6,104 三角面 / 823 B-Rep 面 / 1.38 s，约 350 B/三角面）折算：

| 项 | 测算值 |
|---|---|
| 整线原始 STEP（20~30 个模型） | **2 ~ 6 GB** |
| 整线三角面 | 5 ~ 30 M |
| 单模型 200 MB 的 B-Rep 驻留内存 | **1 ~ 3 GB**（约为文件体积的 5~15 倍） |
| 单模型 200 MB 的解析耗时（WASM 单线程外推） | 约 **130 s**，且内存先崩 |

> 注：模具、锻件属自由曲面密集型模型，单位三角面的 STEP 字节数高于规则机加工件（NURBS 控制点密集），实际面数可能低于按 350 B/面 的线性外推值，但 B-Rep 实体的解析开销更高。

### 2.3 矛盾定位

| 环节 | 路线 A | 路线 B | 判定 |
|---|---|---|---|
| 200 MB 单文件解析 | ❌ WASM32 地址空间上限（4 GB 理论 / 约 2 GB 实际安全线） | ✅ 64 位原生，多线程 | **B 赢** |
| 大场景交互渲染（10 M+ 面） | ✅ WebGL2 + LOD 可稳定 60 fps | ❌ AIS 掉至个位数 fps | **A 赢** |
| ≥10 Hz 轴联动 | ✅ 实测余量约 29 倍 | ❌ 渲染掉帧即违约 | **A 赢** |
| 内存与多线程扩展性 | ❌ 不可扩展 | ✅ 可用满物理内存 | **B 赢** |

**结论：两条路线各自的短板恰好是对方的长处，不存在单一胜出方案。必须按"解析归原生、渲染归 Web"分工，即混合架构。**

## 三、综合方案：三层架构

### 3.1 架构总览

```
① 固定设备（我方离线预处理，交付前一次）
   压机 / 机械臂 / 加热炉 / 液压站 / 产线工装
        ↓  STEP → OCCT 原生离线管线 → 轻量化资产
   资产库：.glb + Draco + LOD×3 + .brep 缓存 + 碰撞代理
        ↓
② 客户模型（运行时按需，本地原生转换服务）★ 关键路径
   模具 / 锻件 / 客户任意 STEP（≥200 MB）
        ↓  前端识别大文件 → 拉起本地原生服务
   转换链：STEP → XDE 装配树 → 三角化 → 简化 → LOD → Draco → 碰撞代理 → 缓存
        ↓
③ 运行时渲染与仿真（three.js + WebGL2）
   按工位按需加载 · LOD · 视锥剔除 · 实例化 · 10 Hz 状态总线
```

### 3.2 第一层：固定设备离线预处理管线

- **对象**：压机、机械臂、加热炉、液压站、产线工装 —— 体量大但**固定不变**。
- **时机**：软件交付前一次性完成，随安装包一并交付。
- **处理内容**：
  1. OCCT 原生解析 → 装配树 + B-Rep 面索引保留；
  2. 三角化（弦高 0.3~0.5 mm）；
  3. 网格简化 + LOD 三级生成；
  4. Draco / meshopt 压缩 → `.glb`；
  5. 生成碰撞代理（OBB 组合 / 凸包 / L2 低模）；
  6. 落盘 `.brep` 二进制缓存（二次加载免解析）。
- **目标**：单件资产 ≤ 10 MB，整线资产 ≤ 500 MB。

### 3.3 第二层：客户模型本地原生转换服务（关键路径）

这是本次方案的核心新增件，直接决定 200 MB 实时导入能否成立。

| 项 | 设计 |
|---|---|
| 触发时机 | 前端检测到导入文件 ≥ 20 MB，自动拉起本地服务（≤20 MB 走前端快路径） |
| 进程形态 | 独立本地进程（Python + OCCT 原生），前端通过本地 IPC / HTTP 调用 |
| 位宽与线程 | 64 位，OCCT 并行网格化，可用满物理内存 |
| 处理链 | STEP → XDE 装配树 → 三角化（容差可控）→ 简化 → LOD → Draco → 碰撞代理 |
| **内存控制** | **单次通过：三角化完成后立即释放 XDE / B-Rep**，峰值内存 = max(B-Rep, 网格) 而非两者之和 |
| 输出 | 轻量化网格回传前端渲染；同时落盘缓存 |
| 缓存键 | 源文件哈希，命中则跳过全部转换 |
| 前端体验 | 拖入文件 → 三阶段进度条（解析 / 三角化 / 优化）→ 场景出现；二次导入秒开 |

> **设计要点**：对客户而言，操作始终是"把模型拖进去"，不感知内部是解析还是转换。这是该架构成立的前提。

### 3.4 第三层：运行时渲染与仿真

- three.js + WebGL2，只消费轻量化结果，不直接接触原始 STEP；
- **按工位/区域按需加载**，严禁 20~30 个模型全量常驻；
- LOD 三级 + 视锥剔除 + InstancedMesh（重复立柱、垫块）；
- 碰撞检测：AABB 粗筛 + BVH 三⻆面精筛，**精筛只作用于简化碰撞代理**；
- 10 Hz 状态总线发布关节 / 位姿 / 碰撞 / 报警，可直接映射为 OPC UA 变量表。

### 3.5 分级导入策略

| 源文件大小 | 处理路径 | 预期耗时 | 用户体验 |
|---|---|---|---|
| ≤ 20 MB | 前端 WASM 直接解析 | 秒级 | 无感知 |
| 20 ~ 200 MB | 本地原生转换服务 | 30 ~ 120 s | 进度条 |
| > 200 MB | 本地原生服务 + 分块流式处理 | 更长 | 进度条 + 分块出现 |

## 四、关键技术措施

| # | 措施 | 作用 | 预期收益 |
|---|---|---|---|
| 1 | **单次通过 + 及时释放 B-Rep** | 三角化后立即释放 XDE 文档 | 峰值内存降至约 1/3，是吃下 200 MB 的决定性一招 |
| 2 | **三角化容差策略**（弦高 0.15 → 0.3~0.5 mm） | 模具/锻件用于路径规划与碰撞，无需高精度网格 | 面数降至 1/2 ~ 1/4 |
| 3 | **碰撞体与显示体分离** | 显示体精细；碰撞仅用 OBB / 凸包 / L2 低模 | 碰撞开销降一个量级 |
| 4 | **LOD 三级 + 视锥剔除 + 实例化** | 远距离与重复件按需降载 | 渲染负载随视距线性下降 |
| 5 | **资产缓存（.brep + .glb 双缓存）** | 文件哈希为键，命中免转换 | 二次导入秒开 |

> 弦高与面数的关系：圆柱面三角面数 ∝ h^(−1/2)，双曲面 ∝ h^(−1)。弦高放宽 3 倍，面数约降至 1/3 ~ 1/6（按曲面类型分布加权）。

## 五、技术栈与规程合规

### 5.1 栈定义

| 层 | 组件 |
|---|---|
| 离线/转换层 | Python 3.11+ · OCCT 7.8 原生 · pythonocc-core 或 OCP · NumPy · trimesh（简化）· Draco |
| 前端层 | Node 18+ · three.js · three-mesh-bvh · Vite |
| 数据接口 | asyncua（OPC UA ≥200 点 / ≥10 Hz） · 变量字典 Excel |
| 外壳 | 见 5.3 |

### 5.2 许可证明细

| 组件 | 许可证 | 闭源商用结论 |
|---|---|---|
| OpenCascade (OCCT) | LGPL-2.1 + exception | ✅ 动态链接可商用；需附许可证与源码获取声明 |
| pythonocc-core | LGPL-3.0 | ✅ 动态链接可商用 |
| PySide6 | LGPL-3.0 | ✅ 可闭源商用 |
| **PyQt6** | **GPL-3.0 / 商业双授权** | ⚠️ **闭源交付必须购买商业许可，禁止误用** |
| three.js | MIT | ✅ |
| three-mesh-bvh | MIT | ✅ |
| Draco | Apache-2.0 | ✅ |

### 5.3 两种外壳方案

| 方案 | 组成 | 包体 | 适用 |
|---|---|---|---|
| **C1 · 技术最优** | Tauri（系统 WebView2）+ Python sidecar | ≈ 50 MB | 客户不强制技术栈时优先 |
| **C2 · 规程合规** | PySide6 + QWebEngineView 承载前端 + 同进程 Python/OCCT 后端 | 0.6 ~ 1.5 GB | 规程（甲方或公司）强制 "OCCT 原生 + Qt/PySide6 + Python" 表述时采用 |

> C2 完全符合"OCCT 原生 + Qt/PySide6 + Python"的技术栈表述，同时保留 three.js 的交互与渲染性能。两种外壳共用同一套转换服务与前端代码，切换成本极低。

## 七、实施计划

| 阶段 | 内容 | 产出 | 周期 |
|---|---|---|---|
| P0 | **200 MB STEP 实测基准**：解析耗时、峰值内存、面数、曲面类型分布 | 实测报告，锁定规格数字 | 1 周 |
| P1 | 本地原生转换服务：CLI + 装配树 + 三角化 + 简化 + Draco + 缓存 | 可命令行运行的转换器 | 2 ~ 3 周 |
| P2 | 前端接入：分级导入判定 + 三阶段进度条 + 缓存读取 | 端到端可导入 200 MB | 2 周 |
| P3 | 离线管线：固定设备预处理 + LOD 生成 + 碰撞代理 | 整线轻量化资产库 | 2 周 |
| P4 | 性能收口：按需加载 + 内存调优 + 长时运行稳定性 | 性能确认单 | 1 ~ 2 周 |

> **P0 必须最先做。** 200 MB 的解析耗时与峰值内存是所有规格数字的来源，也是"这件事能不能做"的判定依据。在没有实测之前，任何规格承诺都存在履约风险。

## 八、风险与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| 200 MB 自由曲面 STEP 解析超时或内存溢出 | 高 | P0 实测先行；原生服务 + 单次通过释放；兜底引入商用内核（CAD Exchanger / HOOPS Exchange）做流式加载，作为单独报价项 |
| 客户文件被企业加密软件保护无法读取 | 中 | 沿用现有文件完整性预检（香农熵判定加密 vs 损坏），给出精确诊断而非笼统报错 |
| 招标人终端为集显 / 低内存配置 | 中 | 按需加载 + LOD + 碰撞代理；规格中写明最低与建议配置 |
| "首次导入需转换"被质疑不满足"实时导入" | 中 | 采用"经转换导入"表述（已在 JT 格式上使用并被认可）；三阶段进度条 + 二次秒开 |
| 规程强制技术栈与交付实物不一致 | 中 | 采用 C2 外壳方案，文档与实物统一，消除评标阶段的实质风险 |
| JT 原生直读 | 低（独立事项） | 维持现有转换桥接策略；若甲方坚持原生直读，需 Siemens JT Open Toolkit 或商用内核授权，单独报价 |
