- 编制：工程智拓 @pm ｜ 2026-09-14 ｜ 依据：01 需求 D-3、开发规程 §4/§5（S-2 POC、S-4 顺序）、S-1 契约

## 1. 为什么是这套架构（结论先行）

四项硬要求：①桌面工控机交付 ②真几何不能只渲染面片（16(2)）③≥10Hz 轴联动 ④碰撞必须几何级判定。

| 候选 | 判 | 原因 |
|---|---|---|
| 纯浏览器栈（three.js + WASM） | ✗ | 工控机离线部署弱、非桌面交付形态、WASM 几何能力浅 |
| PyQt+PyOpenGL 自绘 | ✗ | 渲染底座从零造，成本高效果差 |
| Qt3D | ✗ | 生态萎缩，显示网格管线不成熟 |
| 收费 SDK（HOOPS/Hosm） | ✗ 本期 | 许可成本未询价，违反 D-8 |
| **OCC 内核 + PySide6 外壳 + 内嵌 Web 视图（本地桥传显示网格）** | ✅ | 真 B-Rep 校验+成熟渲染底座+团队 Python 栈 |

## 2. 进程与数据流

```
┌─────────────────────────────────────────────────┐
│ PySide6 桌面外壳（工作台 UI：步骤条/树/列表/日志）  │
│   ├─ QWebEngineView ── 三维视口（three.js 渲染）   │
│   └─ QWebChannel ⇄ 本地 WS ── 双向桥（bridge.py） │
├─────────────────────────────────────────────────┤
│ core/（纯 Python，无 GUI 依赖，可单测）            │
│   config/      参数体系（轴/行程/零点/比例/方向）   │
│   kinematics/   串联移动副+回转副正解/解析逆解、坐标变换│
│   geometry.py  OCC 导入/装配树/B-Rep校验/tessellation│
│   collision.py 碰撞三态（OCC 精判，FCL 备选）      │
│   path.py      路径生成+行程/可达性校核            │
│   project.py   工程文件 JSON 读写（带版本号）      │
├─────────────────────────────────────────────────┤
│ comm/（独立于 core）                              │
│   opcua_client.py  asyncua 客户端，Subscription    │
│   simulator.py     按 S-1 点表自建 OPC UA Server   │
└─────────────────────────────────────────────────┘
```

- **单向数据流**：core 算 → 显示网格推给视口；视口只回传交互事件（拾取/视角）。禁止前端碰几何判定。
- **几何真身在 Python 侧**：拾取请求带 mesh_id+face_id+三角形重心坐标，core 换算回 B-Rep 面上的真实 3D 点与法向。
- **`core/config/` 为包形态（2026-09-16 T03 交付后回填）**：原单文件 `core/config.py` 实测 **488 行**，超 04 §4.5-① 的 300 行上限 → 按 **T03 派单卡（04 §6.3）预授权**的结构拆为 `__init__.py`（只 re-export＋`__all__`）／`schema.py`（字段名常量与 dataclass 定型）／`loader.py`（读盘＋收齐问题＋一次性抛错）／`validate.py`（各节强校验）四件，实测 30／156／104／296 行。**`load_machine(path)->MachineConfig` 的签名与调用形态一字不变**（`from core.config import load_machine` 照旧成立），下游各单无需知道内部拆分。⚠️ 04 **§4.5-⑦ 的包化预授权范围仍只限 `core/kinematics/` 与 `core/geometry/` 两包**——`core/config/` 属**派单卡个案**，其他文件**不得援引**本条自行拆包。
- **`core/kinematics/` 为包形态（2026-09-16 T04 交付后回填）**：原单文件 `core/kinematics.py` 实测 **428 行** > 300 行上限 → 按 **04 §4.5-⑦ 预授权预案**（照预案结构、零自创文件名）拆为 `__init__.py`（只 re-export＋`__all__`，实测 **34** 行）／`fk.py`（`Joint`／`KinematicModel`／`build_model`／`fk`／`resolve_positions`／`raw_to_eng`，**182** 行）／`transform.py`（`Transform4x4` 行主序位姿运算、`CoordFrame`、三坐标系正逆变换、`to_column_major`，**191** 行）／`limits.py`（`Violation`／`check_limits`，**77** 行）。依赖方向单向 `fk → transform`、`limits → fk`，无回环。**`from core.kinematics import fk, check_limits, Transform4x4, Violation` 调用形态一字不变**，下游 T07／T08 无需知道内部拆分；守卫＝`tests/test_public_api_kinematics.py`（§4.5-⑦ 硬要求 3）。**T07 的解析逆解落 `ik.py`**（预案内新增件，**只新增、不碰 T04 已验收的四件**）。⚠️ **`ik` 仍禁数值迭代**（本节 §3 该行口径不变）。

## 3. 模块职责与接口签名（骨架，ZCode 照签名填）

| 模块 | 关键函数 | 签名（定死） |
|---|---|---|
| geometry.py | 导入 | `import_model(path:str)->Assembly`（含 `is_brep:bool, tree:[AssemblyNode], stats:{parts,tris,load_ms}`） |
| geometry.py | 显示网格 | `tessellate(assembly, deflection:float)->list[MeshPart{id,name,vertices:nx3 float32,tris:nx3 uint32,face_map:nx1 int32}]`（face_map=三角形→B-Rep 面 ID 映射，T06 取真值法向的唯一依据） |
| kinematics/ | 正解 | `fk(joint_values:dict[str,float], model:KinematicModel)->dict[str,Transform4x4]` 每部件位姿（**行主序** 16 元素，均在**设备坐标系**内，要上屏再经 `device_to_scene`）；`model` 由 `build_model(cfg:MachineConfig, joints:Sequence[Joint])->KinematicModel` 一次解析后**复用**（实测 `build_model` 9.5 µs、`fk` 189.2 µs／13 节链 ⇒ ⛔ 禁在 T07／T08 的循环里重建拓扑） |
| kinematics/ | 逆解 | `ik(target_pose:Transform4x4)->dict[str,float]`（**解析闭式解，禁数值迭代**；桁架移动副解位置、腕部回转副解姿态，二者解耦；多解按行程/连续性选解；契约 §5.2 下发关节空间目标即靠它）⚠️ **T07 落码时同样需要配置来源入参**（链拓扑与倍率不可能从 `target_pose` 推出），实参形态以届时交付为准并**回填本行** |
| kinematics/ | 校核 | `check_limits(joint_values, cfg:MachineConfig)->list[Violation]`（行程／限位**＋龙门双驱 sync 偏差**，一次返回全部不通过项；行程／容差／倍率**全取自配置**，T07／T08 的「禁发」判据以返回**空表**为准） |
| kinematics/ | 换算 | `raw_to_eng(axis:Axis, raw:float)->float`（契约 §7.4「最高危项」：**工程值＝原始值 × scale × direction − zero_offset**；`scale` 为 null＝回读已是工程值，按 1.0 处理；`zero_offset` 的单位是**工程值**（mm／deg），非原始计数） |
| kinematics/ | 坐标变换 | `model_to_device／device_to_model／device_to_scene／scene_to_device(point, frame:CoordFrame)->Point`（**原点与轴向一律由调用方以 `CoordFrame` 显式给定，代码内不写死**——契约 §7.1 两条均标「待确认」）；`axis_swap_frame(mapping, origin_mm)->CoordFrame` 专治 §7.1「STEP 默认 Z-up、工厂软件常导出 Y-up」的朝向陷阱，**行列式 −1（镜像）即拒**、旋转部分**建框即校验正交归一** |
| collision.py | 三态 | `check(path:list[Segment], clearance_warn_mm:float)->CollisionResult{verdict:'pass'\|'warn'\|'interfere', cases:[{seg_id,part_a,part_b,min_dist_mm,point}]}` |
| path.py | 生成 | `gen_path(points:list[Waypoint])->list[Segment]`（段类型 LINE/JOINT，含长度） |
| project.py | 工程 | `save/load(path)`，JSON schema 版本字段 `"$schema":"proj/v1"` |
| bridge.py | 桥消息 | JSON 协议见 §5 |
| opcua_client.py | 连接 | `connect(endpoint,cfg)->Session`；回读回调 `on_frames(list[Frame])`，Frame=时间戳+各轴工程值 ⚠️ **消歧（2026-09-16 T04 交付后补）**：本行的 **`Frame`＝回读帧**（时间戳＋各轴工程值，T09 落码），与 `core.kinematics.CoordFrame`（**坐标框**＝原点＋旋转，T04 已落码）**同名不同义、两者禁同名**。T04 原先也叫 `Frame`，已自行改名让路（`bd72921`，纯改名无逻辑变动），并在类 docstring 写明「**不得简化回 `Frame`**」。⛔ T09 落码时**禁**把回读帧命名成 `CoordFrame`，也**禁**把坐标框改回 `Frame`——同名不同义在同时 import 两者的模块里会**静默互相覆盖且不报错**（本项目已有 **Q 编号双轨**的前例：契约 §2.2 与《沟通单》两套 Q-1~Q-12 编号相同含义不同，曾出现同一张任务单内混用） |

**铁律**：core 不得 import PySide6/asyncio 之外的 GUI/通讯包；comm 不得 import 三维显示；一切跨界走 bridge 消息。

**⚠️ kinematics 三行签名回填的依据（2026-09-16 T04 收单时由指挥方裁决，非实现会话越界）**

表头写「签名（定死）」，而本轮 `fk` 与 `check_limits` **各多了一个入参**，属对冻结签名的改动，故留此依据：

- **原签名按字面无法实现**：`fk(joint_values)` 与 `check_limits(joint_values)` **没有任何配置来源**——链拓扑（哪根轴驱动哪根连杆、沿哪个坐标轴动）、行程、倍率都无从取得。这是**文档侧的潜在缺陷**（签名先于「`machine.yaml` 缺轴↔连杆绑定字段」这一事实被冻结），不是实现会话的疏忽。
- **三条可选路径各违反什么**：① 把绑定**写死在 `core/kinematics/`** → 违 04 §5.5 常驻复查①（禁轴参数魔法数字）与 T04 卡「禁在代码里写死」；② **给 `machine.yaml` 加字段** → 违 §4 归属矩阵（`config/machine.yaml` 唯一写者＝T03，**任何单不得私改**）；③ **绑定作显式入参** → 只改本表签名。三者必违其一，**③ 损害最小**：它同时保住了「零硬编码」与「machine.yaml 单一写者」两条硬纪律，且回执到达后**只改配置／调用方绑定表、不改 `fk.py`**。
- **程序合规**：会话 A **未自行改设计**——该偏离在其完工汇报里列为「遗留 ⑤，需您裁决」并附了可直接粘的回填文案，属**停下报备**，符合「规格冲突即停下汇报、不得单方面改设计」的纪律。本行即指挥方的裁决落点。
- **连带未决项**：`links` 是否增 `axis`／`motion` 两键（把绑定从 **yaml 注释**升格为**受校验字段**）**尚待 @user 派活并裁决字段名** → 登记为 04 §7.2 **G18**；11 根臂专用轴在 `links` 表里无对应连杆（fk 不出其位姿、碰撞覆盖不到那五套工装）登记为 **G19**（属**问甲方**动作，随踏勘回执一并问）。

**导入与碰撞的性能化处置原则（2026-09-15 吸收《三维模型导入能力综合技术方案》及其审阅意见，随 CR-2026-03 登记）**：
- 导入全走**原生转换链**（装配树→三角化→简化→LOD→轻量化网格→缓存）；**不引入前端 WASM 直解路径**。
- 转换**单次通过**：三角化完成立即释放 XDE/B-Rep，峰值内存 = max 而非两者之和。
- **双缓存**：`.brep`（几何真身，拾取/精判按需重载、用毕可释放）＋ 轻量化网格（显示）；键＝源文件哈希，二次导入秒开。
- **碰撞两段制**：交互预检（可选，前端加速结构作用于简化代理，求快）与权威判定（core 侧 OCC 几何级精判＋保守包络 2–5mm，求准）分离；**预检结论不构成判定、不作为下发依据**。
- **两条导入路径产物形态一致**：固定设备资产走离线预处理管线（交付前一次性，随包交付）；客户模型现场直导走运行时转换链。
- 大模型相关性能数字（解析耗时/内存/面数/二次导入）在 **P0 实测前一律标"暂定"**，不写入对外承诺。
- 运行时按工位/区域按需加载，**严禁整线模型全量常驻**。

**实机轴系口径（2026-09-15 G11 已定，随 CR-2026-03）**：
- 实机 **22 个受控运动轴**（X1／Z1／YA~YE／Y1／X2／Z2／X3／ZA1·ZA2·RA／ZB·FB1·FB2／ZC·FC·RC／ZD·KE）；契约 §5.2 的 8 轴上界（`Pos = ARRAY[0..7]`）与实机不符，**契约升版（扩容＋AxisMask）随 V1.3 窗口处理，软件侧零硬编码、届时只改 machine.yaml 不改码**。
- 轴分两类（`role` 字段）：**轨迹级联动轴**（X1/Z1/Y1/X2/Z2/X3＋所挂臂专用轴，上限 9 轴，逐点参与路径与碰撞校核）与**工序级设定轴**（YA~YE 料架对位，按批次设定，软件只读）。
- **快接换臂 → 工作模式（`modes`）决定当前有效轴子集**：下发段只含当前模式轴；`AxisMask=0` 的轴 PLC 保持当前值（契约原"未用轴位填 0"规则**在 V1.3 后**废止——扩容后填 0 即误动）。
- **过渡期口径（2026-09-15 审计后明确，防"卡内自相矛盾"）**：契约 V1.2 **现状仍是 8 轴布局**（`Pos[0..7]`、"未用轴位填 0"），而扩容与 AxisMask 属 **V1.3 目标形态**。故 **V1.3 冻结前**：段打包按 `opcua.pack_profile=v1_2_8axis`（56 B/段、填 0、无 AxisMask），22 轴全表与 AxisMask **只存在于 machine.yaml 内部**（供校验与将来的 `v1_3_24axis`）；V1.3 冻结后**改 profile 取值即切换、不改码**。**禁把 22 轴硬塞进 V1.2 布局**。
- **X3 倍速链 1:2**（二级筒动 10mm → 三级筒相对一级筒动 20mm）用 `coupling{type: ratio}` 显式表达，禁外部按两倍行程反推。
  - ⚠️ **`master` 自指的判读口径（2026-09-16 定案，随 T03 交付）**：`machine.yaml` 实测为 `{type: ratio, master: X3, ratio: 2.0}`——**master 指向自身**，因为倍速链的主动件（二级筒／伸缩油缸）**不是** 22 轴清单里的受控轴，无第二根轴可指。故判读规则为：**`master == 自身` ⇒ 驱动级倍速**，即「该轴工程位置 = 自身驱动位移 × ratio」；⛔ **禁**读成「X3 = 另一根轴 × 2」的**跨轴约束**。只有 `master != 自身` 时才按跨轴口径（从动轴 = 主动轴 × ratio）。**凡用 fk 的单（T04 正解／T07 逆解与段生成／T08 碰撞校核）都须先判这一支**；ratio 换算必须配置驱动，禁在代码里写死 `* 2`。终局依据＝踏勘确认清单第 4 项回执（软件下发三级筒实际位置，还是由 PLC 按下发值换算），回执后**只改 `machine.yaml`、不改码**。
- 行程/零点/正方向以电气·机械回执为准；回执前样例逐轴标 `pending: true` 占位，加载器对占位**告警不拒绝**。
- **职责边界（2026-09-15 22:43 @user 明确）**：**主要动作由 PLC 编程**；**涉及轨迹编程的工况，由软件输出轨迹参数**（当前工作模式轨迹级轴的段序列：目标位置／速度／过渡方式）交 PLC 执行。软件**不输出整机运动程序**；PLC 负责把轨迹参数接入其主程序（启动条件、与工序动作的衔接、异常中止均由 PLC 侧程序负责）。
